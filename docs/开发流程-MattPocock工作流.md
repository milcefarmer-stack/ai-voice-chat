# AI 协作开发流程(Matt Pocock 工作流落地版)

> 来源:Matt Pocock(Total TypeScript 作者,GitHub 18 万星)开源的 AI 协作 skill 集,
> 按文章《只用五行字把失控的 AI 治得服服帖帖》整理成可直接照做的流程。
> 适用工具:Claude Code / Codex / Cursor / Hermes Agent 均可,思路通用。
> 本文件为完整参考版;执行时遵循根目录 AGENTS.md 的精简版。

## 流程总览

```
口述想法 → ①grill 拷问 → ②to-spec 规格书 → ③to-tickets 任务拆分
        → ④implement(TDD 实现)→ ⑤code review(独立会话)
        → ⑥每周 improve-codebase 架构大扫除 → 回到 ①
```

---

## 第 0 步:配置 skill(一次性)

把 5 个 skill 装进你的 AI 工具(Claude Code 的 `.claude/skills/` 或对应机制):

| Skill | 作用 | 一句话精髓 |
|---|---|---|
| grill-me / grill-with-docs | 需求拷问 | 共识没达成前,把人往死里问 |
| to-spec | 写规格书 | 规格里禁止出现代码 |
| to-tickets | 拆任务 | 按用户功能拆,不按技术层拆 |
| implement | TDD 实现 | 先写测试(红灯)再写代码(变绿) |
| code-review | 独立审查 | 开全新会话,按 12 种坏味道清单查 |

没有现成 skill 机制?直接把每步的"提示词核心"存成文件,用时粘贴即可(见文末模板)。

## 第 1 步:Grill —— 让 AI 把你拷问到崩溃

**做什么**:用自己的话口述需求,AI 只准提问不准写代码。

**规则**(grill-me 的五行核心):
- AI 像心智图一样顺着你的每个决定追问
- 每次只问一个问题
- 每个问题必须附上 AI 自己的建议答案
- 所有关键决策你拍板之前,禁止碰任何代码

**示例**:你说"做个购物车",AI 会追问:
"商品保存多久?关浏览器还在吗?双设备要同步吗?库存不足允许超卖吗?"

**为什么**:写程序 = 连续几百个微观决策。模糊需求丢给 AI = 决策权外包给黑盒子,它一定选最偷懒的做法。

**2026.7 更新**:Matt 已不再默认推荐 grill-me,改推 **grill-with-docs**(拷问同时维护 CONTEXT.md 和 ADR 架构决策记录);复杂大需求用 **wayfinder**(先扫描代码库 → 并行跑多个 grilling 会话 → 输出决策完备的 spec)。

## 第 2 步:To-Spec —— 把共识锁死成规格书

- 把吵架吵出来的所有共识写成一份规格文档
- **铁律:规格书里禁止出现任何程序代码**
- 只回答一个问题:这个功能到底要解决什么?
- 为什么禁代码:文件永远跟不上代码变化,过期规格会把 AI 搞精神分裂

## 第 3 步:To-Tickets —— 切成 AI 嚼得动的小块

- **按用户功能拆,不按技术架构拆**
- ❌ AI 天生爱拆:先数据库 → 再后端 → 最后前端(最后才能测试,全赌一次)
- ✅ 正确拆法:"会员登录" = 表+逻辑+界面一个任务;"购物车" = 一个完整任务
- 每个任务做完 = 一个可以实际点开测试的产品增量
- 互不依赖的任务可以并行分给多个 AI 会话

## 第 4 步:Implement —— TDD 防 AI 作弊

**顺序绝对不能反**:
1. AI 先写测试:"满 1000 必须扣 100" → 跑,红灯
2. 再写实现代码 → 写到测试变绿为止

**为什么**:先写代码后补测试,AI 会拿自己写错的逻辑配一个必过的测试(扣 200 也给"通过"),你永远抓不到 bug。测试先定死,作弊空间归零。

## 第 5 步:Code Review —— 开新会话,按清单查

- 用**全新的对话 session** 审查(避免写代码时的记忆干扰)
- 审查标准 = 《重构》12 种坏味道清单,重点:
  - Shotgun Surgery:改一处要同时改十几处
  - Feature Envy:逻辑放错了位置
  - Data Clumps:几个变量总绑一起出现却没人打包
  - (其余:重复代码、过长函数、过大类、发散式变化、依恋情结、基元偏执、switch 惊悚现身、临时字段、消息链、中间人、夸夸其谈通用性)

## 第 6 步:每周大扫除 —— improve-codebase-architecture

- 每隔几天跑一次,对每个模块问:"把这个模块删掉,让主程序接管,会怎样?"
- 删掉天下大乱 = 深模块,真在做事,留下
- 删掉代码反而清爽 = 浅模块空壳,清掉
- 生成 HTML 架构诊断报告,看图挑一处 → "照这个方案重构"

## 写 Skill 的三原则(writing-great-skills)

1. **修剪 Pruning**:废话、AI 本来就知道的常识指令,全删
2. **术语指代**:一个专业词 > 一百字解释(说 "Data Clumps" 秒懂)
3. **完成标准**:明确告诉 AI "做到什么程度算完"

核心:多写一句废话,AI 多一分分心。

## 附:不用 skill 机制的最简模板(直接粘贴用)

**拷问**:
> 在我们对计划达成完全共识前,禁止写任何代码。一次只问一个问题,每个问题附上你的建议答案,直到所有关键决策我已拍板。

**规格**:
> 把我们的共识整理成规格文档。禁止出现任何代码,只回答"这个功能解决什么问题"。

**拆任务**:
> 把规格拆成任务清单。按用户可见的功能拆(每个任务含数据+逻辑+界面,做完即可测试),禁止按技术层拆。

**实现**:
> 严格 TDD:先写测试并运行确认失败(红灯),再写实现直到测试通过(绿灯)。禁止在测试前写实现代码。

**审查**:
> 开一个全新会话(不带写代码的记忆),按《重构》12 种坏味道逐项检查这次改动,只报告有实据的问题。

## 一句话总结

AI 时代真正值钱的不是 prompt 技巧,是你领域内的专业判断:决策权在人(grill)、共识入文档(spec)、增量可测试(tickets)、测试先于代码(TDD)、独立会话审查(review)、定期架构清扫(扫除浅模块)。
